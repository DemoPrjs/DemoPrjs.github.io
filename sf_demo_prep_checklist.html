Dev Checklist — Front End
Community Portal & application-facing components
▾
Portal Header
Community portal header includes: profile menu, notifications, Contact Us link, Login/Logout, Registration with MFA
Email Templates
All email templates use a generic (non-personal) email address as the sender — no individual dev or test email addresses
UI & Pages
Landing home page has a rich, polished UI — not a bare default page
Application dashboard has a rich, polished UI
Application Dashboard
Dashboard shows a pizza tracker (visual step-by-step progress indicator) for application status
Dashboard includes a comments component where users and staff can communicate
Users can save an application as a draft (Save for Later) and come back to finish it
Application details open via a double-click on "View Details" — not a standard button click
Form fields are auto-populated from uploaded documents — user should not need to re-enter data already in a file
Data & Users
All test data looks realistic — no placeholder text like "Test", "Test User", "Test Application", "ACME", etc.
A dedicated demo user account is created — separate from dev and QA users to avoid data or permission conflicts
Demo user has all required permissions and profile settings configured — test the user login before the demo day

Dev Checklist — Back End
Case management, automation, reporting
▾
Guidance for Success is configured and displayed when a case changes status — staff should see clear next-step instructions at each stage
In-App Notifications are set up and working — users receive alerts inside the platform when their case moves forward
Back-end pizza tracker shows the current case status visually for the staff/agent view
Reports and dashboards are built and populated with realistic demo data — no empty charts or tables
Document Generation is working — the system can produce a document (e.g. letter, decision notice) from a case
Email alerts are triggered automatically when a case is updated — test at least one full email flow end-to-end
Demo user has all required back-end permissions and access (record types, queues, profiles, permission sets)
Back-end test data is realistic — no generic placeholders like "Test Case", "Test Record", or "Lorem Ipsum"

Dev Checklist — Environment & Code
Repo hygiene, code freeze, deployment readiness
▾
A dedicated GitHub repository is created for the demo — separate from any shared dev or sprint repo
All settings and values are configurable via metadata or custom settings — no hardcoded IDs, URLs, or credentials in the code
Give sufficient time for a code freeze before the demo — no new deployments or changes after the freeze date
